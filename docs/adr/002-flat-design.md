# ADR-002: Выбор дизайна

## Статус
Принято (Accepted)

## Контекст
Мы разрабатываем легковесное клиентское веб-приложение для генерации монстров на основе эмодзи. 
Основные требования:
* Высокая скорость разработки (MVP).
* Минимальный размер бандла для быстрой загрузки на мобильных устройствах.
* Простая логика реактивности (связывание выбранных эмодзи с визуальными элементами монстра).

## Решение
1. Использовать классическую **плоскую структуру папок с директорией `src/components/`** вместо сложных архитектурных методологий.

## Рассмотренные альтернативы
* **Feature-Sliced Design (FSD)**: Отклонено. Приложение состоит из одной ключевой фичи (генератор). Разделение на слои (pages, widgets, features) создаст избыточную вложенность файлов и замедлит разработку.

## Последствия
* **Плюсы**: Кодинг-агент и разработчик видят все компоненты в одном месте. Нет путаницы с импортами. Быстрый старт.
* **Минусы**: При масштабировании приложения (например, добавление соцсети для монстров, личных кабинетов, чатов) папку `components/` придется рефакторить и делить на модули. Скорее всего масштабирование не будет рассматриваться.
